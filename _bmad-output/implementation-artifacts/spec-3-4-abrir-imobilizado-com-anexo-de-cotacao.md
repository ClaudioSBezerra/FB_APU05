## Intent

**Problem:** FR-8/FR-11 — solicitante não tem como abrir um Imobilizado; `AbrirSolicitacaoHandler` só aceita `tipo_solicitacao` em `{transferencia, inclusao_sfc, inclusao}`, `solicitacao_lancamentos` exige `conta_id`/`mes` (incompatível com "classe de imobilizado, não conta contábil, sem mês/competência") e não existe nenhum módulo de anexo (`backend/internal/anexos`, AD-13) nem tabela `solicitacao_anexos`.

**Approach:** Estender o MESMO handler/dispatch (nunca reimplementar) para `tipo_solicitacao="imobilizado"`: reaproveita `AutorizadorNominal`/`autorizadores_formulario` (MESMO motor e MESMA tabela da Story 3.3 — FR-11 agrupa inclusão+imobilizado+obras sob o mesmo mecanismo nominal; `aprovadores_obra`, citada separadamente no inventário de dados, é a única tabela própria de Obras). Linha de Imobilizado troca `conta_id`/`mes` por `classe_imobilizado_id` (valida contra `classes_imobilizado`, cadastro já administrável desde o Epic 2). Novo módulo único `backend/internal/anexos` (AD-13: `Salvar`/`Recuperar`) grava `solicitacao_anexos` (metadado + hash SHA-256 + bytes em `BYTEA`, sem infraestrutura nova de storage); o mesmo endpoint JSON aceita uma lista `anexos` com conteúdo em base64, exigida (≥1) exclusivamente para `imobilizado`.

## Boundaries & Constraints

**Always:** `Resolver.Resolve` continua o único ponto de cálculo (AD-1), via `AutorizadorNominal` (AD-2) para `imobilizado`, MESMA tabela `autorizadores_formulario` da Story 3.3 (CC/faixa de valor, sempre pessoa). Toda linha de Imobilizado é 1 única linha `lado="destino"` (mesmo padrão de Inclusão/Inclusão SFC — Boundaries "Never"). `classe_imobilizado_id` é obrigatório por linha e deve existir em `classes_imobilizado`; `conta_id`/`mes` não se aplicam a `imobilizado` (nunca validados/gravados para esse tipo). Toda solicitação `imobilizado` exige ao menos 1 anexo (`len(anexos) >= 1`) para ser criada — anexo inválido ou ausente bloqueia a gravação por completo (mesma transação: solicitação+lançamento+anexos, tudo ou nada). Upload de anexo passa exclusivamente pelo módulo único `backend/internal/anexos` (`Salvar`/`Recuperar`, AD-13); nenhuma outra lógica de persistência de anexo no handler. `solicitacao_anexos` sempre grava hash SHA-256 + nome + content-type + tamanho, junto com os bytes.

**Never:** Reimplementar `ResolverParaTipo`/o handler/`AutorizadorNominal` — só estender o switch/guard existentes e reaproveitar a mesma tabela de autorizadores. Introduzir tabela de autorizadores separada para Imobilizado (diferente de Obras, que já tem `aprovadores_obra` própria no inventário de dados — isso é escopo da Story 3.5, não desta). Expor campo de fornecedor ou mês/competência no corpo de Imobilizado. Implementar `obras` (Story 3.5) — qualquer tipo fora de `{transferencia, inclusao_sfc, inclusao, imobilizado}` continua 400. Introduzir storage externo (disco/S3/bucket) — nenhuma infraestrutura nova além do Postgres já existente; AD-13 fixa a interface (`Salvar`/`Recuperar`), não o backend físico. Expor endpoint HTTP de leitura de anexo (`Recuperar` é só contrato do módulo, chamado por código, não roteado — nenhum FR/AC desta story exige download via HTTP).

- Testes: `solicitacoes_test.go`, `anexos_test.go`, `calculado_test.go` -- cobrem I/O Matrix do handler, módulo de anexos e dispatch

**Acceptance Criteria:**
- Given um solicitante autenticado, when ele abre um Imobilizado escolhendo uma classe de imobilizado válida e tenta enviar sem anexo, then o sistema recusa o envio com 400 citando a falta de anexo de cotação, nada é gravado.
- Given um solicitante autenticado, when ele abre um Imobilizado com classe válida, `autorizador_id` válido para o CC/faixa de valor e ao menos um anexo com conteúdo base64 válido, then a solicitação é criada com 201, o aprovador é `Tipo="pessoa"` e o anexo é persistido em `solicitacao_anexos` com hash SHA-256 correspondente ao conteúdo decodificado.
- Given o corpo de uma solicitação de Imobilizado, when o formulário é inspecionado, then não há campo de fornecedor nem de mês/competência expostos ou exigidos para esse tipo (apenas `classe_imobilizado_id`, `valor`, `autorizador_id`, `anexos`).
- Given um `autorizador_id` sem linha ativa em `autorizadores_formulario` cobrindo o CC/faixa de valor da solicitação de Imobilizado, then 400, nada é gravado -- mesma tabela e mesmo comportamento da Story 3.3, nunca um aprovador inventado.

## Design Notes

**Imobilizado reaproveita a MESMA tabela `autorizadores_formulario` de Inclusão, não uma lista própria:** FR-11 agrupa explicitamente `inclusão`, `imobilizado` e `obras` sob "autorizador nominal... validado contra lista fixa por CC/faixa de valor" como um único mecanismo; o inventário de dados do domínio (`docs/referencia/02-REQUISITOS-NEGOCIO-ENVIO-TI.md:20`) lista `autorizadores_formulario` uma única vez (não uma por tipo) e cita `aprovadores_obra` como a ÚNICA tabela própria adicional -- exclusiva de Obras (Story 3.5), nunca de Imobilizado. Nenhuma coluna de escopo/tipo existe ou é necessária em `autorizadores_formulario`: um autorizador cadastrado ali vale para qualquer tipo que use `AutorizadorNominal` hoje (`inclusao`, agora `imobilizado`) dentro do mesmo CC/faixa -- é uma decisão de dados do negócio (quem cadastra cada linha), não uma lacuna técnica.

**Anexo decodificado em base64 dentro do MESMO corpo JSON, não multipart/novo endpoint:** o handler `AbrirSolicitacaoHandler` é um único endpoint JSON reaproveitado por todos os tipos (Boundaries "Never" de 3.1-3.3: nunca reimplementar). Introduzir `multipart/form-data` só para Imobilizado duplicaria o parsing de corpo e o guard de tipo. Base64 dentro do mesmo JSON mantém um único contrato de requisição e uma única transação atômica (solicitação + lançamento + anexos, tudo ou nada) -- trade-off aceito: +33% de overhead de payload, mitigado pelo aumento do teto de `MaxBytesReader`.

**Armazenamento de anexo em `BYTEA` no Postgres, não disco/S3:** AD-13 fixa a interface do módulo (`Salvar`/`Recuperar`) e deixa o mecanismo físico de storage como decisão de implementação ("mecanismo base... já está decidido" refere-se à interface, não ao backend). Não há volume de disco, variável de ambiente ou bucket já configurado em `docker-compose.yml`/`.env.example` para anexos -- introduzir um novo exigiria uma decisão de infraestrutura fora do alcance de um agente não supervisionado. Gravar os bytes em `BYTEA` dentro da mesma transação do Postgres (já a única infraestrutura do projeto) mantém a atomicidade exigida pelas Boundaries sem abrir uma nova superfície operacional. Antivírus/DLP/quarentena permanecem fora de escopo (PRD Questão Aberta 3, já deferido na arquitetura).

**`Recuperar` implementado mas não roteado via HTTP:** AD-13 nomeia `Salvar`/`Recuperar` como o contrato público do módulo; implementar só `Salvar` deixaria o módulo incompleto frente à sua própria interface declarada. Nenhum FR/AC desta story exige download de anexo por HTTP (mesmo precedente de 3.1-3.3: nenhum endpoint de leitura é exposto além do necessário) -- `Recuperar` fica disponível para uso futuro (ex. Epic 4/5, fila do administrador revisando a cotação) sem rota própria nesta story.
