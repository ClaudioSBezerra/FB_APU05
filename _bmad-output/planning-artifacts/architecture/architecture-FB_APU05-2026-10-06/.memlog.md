- (decision) Paradigma: hibrido. Nucleo de dominio isolado (ports-and-adapters leve) especificamente para o motor de aprovacao (resolver calculado + autorizador nominal) e a camada de exportacao SAP (interface unica, 5 tipos de solicitacao chamam o mesmo ponto de entrada). Resto do sistema (CRUD de cadastros, fila do admin) segue o padrao Handler Factory simples ja validado no FB_APU02 (sem framework de rotas, SQL puro, services/middleware/migrations).
- (decision) [ADOPTED] Infra/deploy: Coolify para ambiente de testes (mesmo padrao do FB_APU02 - Docker + Traefik). Deploy de producao via GitHub Actions para servidor AWS, mesmo processo/pipeline do FB_APU02 (testar -> build de imagens -> deploy self-hosted com health-check).
- (decision) Nucleo de dominio confirmado sem objecao: interface unica Resolver (motor de aprovacao) com 2 implementacoes (ResolverCalculado, AutorizadorNominal), dispatch por tipo de solicitacao - os 5 handlers nunca calculam aprovador sozinhos. Interface unica ExportadorSAP com 2 implementacoes (ExportadorVBA hoje, ExportadorAPI futuro) e 2 metodos (lote Despesa, lote Obra).
- (decision) Carga Senior (colaborador x CC): upload manual de arquivo CSV por tela do administrador (nao job agendado, nao acesso direto a banco/view). Mesmo padrao de parsing da carga inicial de cadastros mestres (UTF-8 BOM, separador ;).
- (decision) [ADOPTED] Estrutura de repositorio identica ao FB_APU02: backend/ (Go, handlers/services/middleware/migrations), frontend/ (React/TS/Vite/shadcn), docker-compose.yml na raiz, mesmo repo unico FB_APU05 (nao monorepo multi-servico).
- (decision) [ADOPTED] Stack de versoes herdado do FB_APU02 em producao ativa (ultimo commit 2026-10-05, mesma organizacao): Go 1.22, PostgreSQL 15, React 18.3.1 + TypeScript 5.2.2 + Vite 5.2, Tailwind+shadcn/ui, golang-jwt v5, bcrypt custo 14. Verificacao feita por inspecao direta do sistema irmao em producao, nao apenas conhecimento de treinamento.
- (decision) [ADOPTED] Autorizacao: single-company (Ferreira Costa), sem necessidade de multitenancy por company_id como no FB_APU02. Middleware de perfil (solicitante/administrador) a partir da sessao Keycloak, nunca do payload (ja herdado da decisao de auth do PRD).
- (decision) Writer path unico: snapshot de aprovacao e o campo 'versao' (lock otimista) de solicitacoes so podem ser escritos atraves do modulo de dominio (Resolver/motor de aprovacao), nunca por SQL direto de um handler - previne dois handlers divergindo em como gravam uma decisao de aprovacao.
- (question) Deferred (fora do escopo desta spine, heranca de Questoes Abertas do PRD): repositorio de anexos (antivirus/DLP/quarentena), topologia de hospedagem/dominio/proxy/observabilidade, estrategia de rollback de app e banco, HA/backup/restore do Postgres de producao, tenant/claims/grupos exatos do Keycloak para este modulo, formato final da API SAP (dependencia externa, nao definida).
- (event) Reviewer gate rodado (4 subagentes paralelos: reconciliacao, rubric walker, verificacao de versoes, adversarial). Usuario resolveu a unica contradicao real (topologia de deploy - AD-10 corrigido para Coolify=producao, staging separado, AWS=espelho secundario, replicando o FB_APU02 de verdade). Todos os demais findings corrigidos diretamente: AD-2 ganhou formato explicito de Aprovador + regra 'nunca inventar aprovador' + dispatch compartilhado; AD-3 ganhou assinatura/granularidade de lote; AD-4 ganhou backstop de enforcement via REVOKE/GRANT; AD-5 ganhou envelope de erro 409; AD-7 ganhou derivacao de claim Keycloak + protecao do ultimo admin; AD-8 teve escopo delimitado vs CC_EXCECAO; AD-9 passou a citar middlewares de seguranca herdados e o debito tecnico do Go 1.22; 4 ADs novos criados (AD-11 SLA, AD-12 geracao xlsm, AD-13 anexos, AD-14 paginacao); Stack table completada; Capability Map e Deferred atualizados. lint_spine.py limpo.
- (event) spine finalized
- (decision) AMENDED AD-7 (2026-10-06, durante investigacao da Story 1.2): perfil solicitante/administrador passa a ser coluna gerenciada pela aplicacao (tabela usuarios, mesmo padrao do users.role do FB_APU02), nao mais derivado de role/claim do Keycloak. A versao original era incompativel com FR-2 (conceder perfil + proteger ultimo admin exige que o proprio sistema controle essa coluna, nao apenas leia uma claim read-only do Keycloak). Identidade (quem e) continua vindo do Keycloak via e-mail verificado; autorizacao (o que pode fazer) vem do banco.
