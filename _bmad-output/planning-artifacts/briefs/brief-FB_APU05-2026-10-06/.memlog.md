- (decision) Motivacao 'por que agora': sair de planilhas/VBA para um sistema de verdade. Integracao com SAP evoluira para API propria (a ser construida pelo lado SAP), nao apenas o robo VBA atual.
- (decision) V1 sai com a exportacao atual (arquivo + robo VBA) como ponte; integracao via API SAP e responsabilidade de outro time (gestor de integracao SAP como contato), fora do escopo deste projeto. Nucleo do FB_APU05 deve isolar a camada de exportacao (interface pluggable) para trocar VBA por API sem reescrever o dominio.
- (decision) Prazo alvo: pronto ainda em outubro/2026 (este mes). Criterio de sucesso = usuarios abandonarem o processo atual (apelidado 'Jira', burocratico). Lancamento: todos os 5 tipos de solicitacao de uma vez, sem piloto faseado.
- (assumption) RISCO SINALIZADO (nao resolvido): prazo de ~3-4 semanas + 5 tipos simultaneos + zero piloto, para um dominio com motor de aprovacao de duas camadas, 37 tabelas e SSO/Entra ainda nao definido. Mary (analyst) recomenda que PM/Architect tratem isso explicitamente no PRD, nao apenas aceitem o prazo.
- (decision) Autenticacao: reaproveitar o padrao ja validado em producao no FB_APU02 - SSO via Keycloak real da Ferreira Costa (OIDC/PKCE contra https://iam.fcxlabs.com/realms/ferreiracosta), validacao JWKS, FB_APU05 emite seus proprios tokens (JWT 30min + refresh cookie) sem expor o token do Keycloak ao resto do sistema. Isso resolve a lacuna 'SSO/Entra nao definido' do pacote envio TI.
- (decision) Publico: usuarios internos da Ferreira Costa, ~500 pessoas. Lancamento direto para todo esse publico (sem piloto faseado por divisao/tipo de solicitacao).
- (decision) Prazo: ideal este mes (out/2026), mas o usuario aceita ultrapassar se necessario para entregar tudo (5 tipos completos) de uma vez - prazo e 'alvo forte', nao corte de escopo. Risco de auth foi reduzido (padrao Keycloak ja existe e testado no FB_APU02); risco remanescente e volume de regras de negocio (37 tabelas, motor de duas camadas de aprovacao) em prazo curto.
- (decision) Criterio de sucesso final: abandono pratico do processo atual (planilha Jira + VBA), sem meta numerica formal. Secao Risco e Mitigacao incluida oficialmente no brief (nao so no addendum).
- (decision) CORRECAO DE ESCOPO: usuario confirmou que as 14 lacunas do pacote envio TI NAO devem ser cortadas do lancamento - tudo entra, mesmo que estenda o prazo alem de outubro/2026. Fora da v1 fica restrito ao que depende estritamente da API SAP externa (que este projeto nao controla): a propria integracao via API e a consulta online de saldo/bloqueio de ordem no SAP. Lacunas de dados (ex.: 877 pares filial x CC sem alcada, CD Jaboatao sem estrutura) sao responsabilidade de cadastro do negocio, nao do codigo - o sistema deve suportar o fluxo assim que o cadastro existir e sinalizar claramente quando nao existir, mas resolver o cadastro em si nao e tarefa de engenharia.
